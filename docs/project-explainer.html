One rulebook for every AI coding agent.

Rules every agent reads, locks an agent cannot open, and spot checks that show whether the rules held. On top of the rules, skills and a small engine plan the work in slices, route each slice to an agent, and mark it verified only from a check that ran.

Fig. 1. The whole system on one page

You write the rules once. The harness freezes them as a numbered release and puts the same text where each agent reads it. Skills add detailed procedures, and the engine records what each agent did.

Solid lines are commands in this repo. Dashed lines are a paste that only you can do, and test sessions.

Why it exists

The problem

  • Each agent keeps its rules in a different place. Claude Code reads a file in ~/.claude. Codex reads a file in ~/.codex. Cursor reads a setting inside the app. A cloud agent sees only the project folder.
  • Copies drift. You change one by hand, and the others fall behind. Then no one knows which edition an agent has.
  • Written rules are advice. A model can ignore them.
  • A file in the right place does not prove that an agent follows it.

The answer

Rules
One policy, frozen as an approved release. Every agent gets the same text, and its first line names the edition: Harness release 1.5.9.
Locks
A few actions are refused, or stopped for your OK, by the agent's own software. Today that is Claude Code only.
Proof
Three separate levels: configured, tested, behaviorally verified. A file check is never reported as proof of behavior.
Work
Skills and the ae engine split work into slices, route each slice to an agent, and keep the evidence. A slice is verified only when the engine saw its check pass.

The limit stays visible on every page of this project: rules guide a model. They cannot force it.

Fig. 2. Advice, ask rule, lock

A rule has a strength. Advice asks the model. An ask rule makes the software stop and ask you. A lock makes the software refuse. A release needs your approval before anything happens.

  1. Advice

    The rule asks. The model decides.

    Every platform.

  2. Ask rule

    The software stops and asks you.

    8 rules, Claude Code.

  3. Lock

    The software refuses.

    19 rules, Claude Code.

  4. Your approval

    Nothing happens until you approve the exact text.

    Every release.

A lock matches the text of a command. It is a guard, not a sealed room: an unusual form of the command can still pass.

    Model strategy, as written today
    
      
      
        
    • A plan gives each slice an agent, a model, and an effort, for example Codex (auto) or Claude (opus/high). Source: multi-agent-planning/SKILL.md.
      • 
        
    • Codex and Cursor stay in auto and pick their own model. The lead checks what the host offers before it names a Claude model. Model names, quotas, and costs are never invented.
      • 
        
    • There is no fixed cap on subagents. A child starts only for independent work. Its model is chosen by accuracy first, then speed, then usage. Source: subagent-budget/SKILL.md.
      • 
        
    • The reviewer is a different session from the builder. After a failed check, the effort or the model goes up one step, with a stated reason.
      • 
      
    
      
    These are instructions to the agents. The ae engine records state and evidence. It does not choose models.

      Set it up
      
    
      You need Node.js 24 or later, npm, and Git, and the command-line program of each agent you use. Run every command from the repo folder. You set it up once. After that, the agents read the rules by themselves at every start.
      

    
      The short path: five minutes, no global file touched
      
    
      Put the policy into a scratch folder, check it, search the references, and take it out again. Run it after npm ci.
      
    
      npm run harness -- activate 1.5.9
DEMO=$(mktemp -d)
npm run harness -- repo install "$DEMO"
npm run harness -- repo verify "$DEMO"
head -n 8 "$DEMO/AGENTS.md"
npm run harness -- search 'tracer bullet'
npm run harness -- repo uninstall "$DEMO"
      
    
      You should see "configurationVerified": true from repo verify, the "Tracer bullets" section with a citation from search, and only the harness block removed by repo uninstall.

      Why it is built this way
      
    
      
      
      DecisionWhyWhat it costs
      
      
        
      You approve a digest, not “the latest”.You see the exact text that every agent will get. A change after the preview stops the publish.One more step for every change.
      
        
      A release never changes.Every install can be compared with a known text. To go back is one command.A one-word fix needs a new version number.
      
        
      A small core, with detail on demand.The policy loads in every session, so every line costs context. Skills and references load only when used.The agent must choose to look things up.
      
        
      In an instruction file, the harness owns one marked block.Your own text in the same file stays. Every write has a backup, a receipt, and an undo.Uninstall refuses when you edited the file after the install.
      
        
      Locks sit outside the model, with a lock on the locks.A refusal that does not depend on what the model decides. The edit tool and the controls command are refused too.Claude Code only. A lock matches command text, so an unusual form can pass.
      
        
      A file check never counts as proof of behavior.“Configured” and “verified” stay different words in every report.Proof needs a real session, and that spends tokens.
      
        
      Cursor gets the rules in one place, by hand.With a rule file as well, the policy loaded twice in every chat, and the two copies differed after each release.One paste for each release.
      
        
      No framework, and two runtime dependencies.Node.js 24 runs the TypeScript directly. There is less to install and less to audit.It needs Node.js 24 or later.
      
        
      A slice is verified only from a check the engine ran.An agent's "done" is a claim. The engine keeps the command, the exit code, and the Git head.A sign-off by a person is a separate state, ACCEPTED.
      
        
      The engine has no commit grant.Authority comes only from you. A typed commit, push, merge, or pull request stays your decision.An unattended run ends with uncommitted work and a report.
      
        
      The reference search is read-only.An agent can read approved documents. It cannot publish or run a command through the search.It runs on your computer only. Cloud agents have the rules but no search.

      Words used here
      
      
      
        
      Agent
      An AI program that reads, writes, and runs code for you.
      
        
      Harness
      This repo: the rules, their delivery, the locks, and the spot checks.
      
        
      Policy
      The text of the rules.
      
        
      Release
      A numbered, frozen edition of the policy.
      
        
      Digest
      A fingerprint of the exact text. One changed letter changes it.
      
        
      Install
      To write the policy where an agent reads it.
      
        
      Receipt
      A record of what an install wrote, with a backup of what was there before.
      
        
      Session
      One conversation with an agent, from start to finish.
      
        
      Skill
      Instructions that an agent loads only when a task needs them.
      
        
      Spot check
      A test task with fixed checks, run in a fresh session. The code calls it an eval.
      
        
      Slice
      One part of a plan, with its own check. It moves from planned to verified.
      
        
      Journal
      The engine's record of each slice: its state, its history, and its evidence. A file next to the plan.
      
        
      Charter
      Your typed approval for an unattended run, with a deadline and attempt caps.
      
        
      Engine
      The ae program. It records each slice's state and evidence.
      
        
      MCP server
      A small helper program. Here it lets an agent search the references.
      
        
      Cloud agent
      An agent on a remote computer that sees only one project folder.
